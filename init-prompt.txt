# Colony Shell — Session Initialization

You are the coding agent for Colony Shell, a POSIX-compliant shell written in Rust. Before doing any work, you must initialize and sync with the project's tracking system.

## First-Time Setup

If `.claude/system/` does not exist, create it with the following structure:
```
.claude/
└── system/
    ├── features.json      # Feature tracking
    ├── history.txt        # Work log
    └── rules.txt          # Project constraints and scope
```



### Create history.txt
```
# Colony Shell — Development History
# Format: [YYYY-MM-DD HH:MM] ACTION: Description
# Actions: START, PROGRESS, COMPLETE, BLOCKED, DECISION, REFACTOR, BUG, FIX

[YYYY-MM-DD HH:MM] START: Project initialized
```

### Create rules.txt
```
# Colony Shell — Project Rules and Constraints

## Scope

1. This is the SHELL component only — no terminal rendering, no GUI, no TUI widgets
2. POSIX compliance is mandatory for core shell features — real bash/zsh scripts must work
3. Agent features are additive — the shell works without AI integration
4. All AI memory lives locally — never send to external services without explicit user action
5. Communication with colony-terminal happens via OSC 2337 escape sequences only

## Technical Constraints

6. Use nix crate for Unix syscalls, not raw libc
7. Use parking_lot over std::sync for mutexes (smaller, faster)
8. Use scc::HashMap for concurrent collections (better scaling than DashMap)
9. Use thiserror for library errors, miette for user-facing diagnostics
10. Use tokio for async runtime, but fork/exec requires spawn_blocking
11. Feature-gate heavy dependencies: --features agent, --features mcp
12. Parser must be hand-written (recursive descent) — parser generators can't handle shell grammar
13. Lexer needs mode stack for context-sensitive tokenization

## Code Quality

14. All public APIs must have doc comments with examples
15. Test POSIX compliance by comparing output with bash
16. Integration tests for each feature before marking complete
17. No unwrap() in library code — propagate errors properly
18. Use tracing for structured logging, not println!

## Architecture

19. Crate separation: parser, expand, exec, protocol, agent, memory, tuple, mcp, focus
20. Each crate should be independently testable
21. Protocol types shared between shell and terminal via colony-protocol crate
22. Memory operations are async — don't block the shell on vector search

## Non-Goals

23. NOT building readline/line editing — will use reedline crate
24. NOT building completions — terminal handles display, shell provides candidates
25. NOT implementing bash-isms unless POSIX-compatible (no [[ ]], no (( )) outside $)
26. NOT supporting Windows (Unix-only via nix crate)
```

## Session Start Protocol

At the beginning of EVERY coding session, execute these steps IN ORDER:

### 1. Check Git Status
```bash
git status
git log --oneline -10
```

Review what's changed since last session. Note any uncommitted work.

### 2. Read System Files
```bash
cat .claude/system/rules.txt
cat .claude/system/features.json
tail -50 .claude/system/history.txt
```

Understand: What are the constraints? What features exist and their status? What was done recently?

### 3. Identify Current Focus

From features.json, find:
- Features with status "in_progress" — these are active work
- Features with status "blocked" — check if blockers are resolved
- Next "new" feature by priority (lowest number = highest priority) whose dependencies are "complete"

### 4. Announce Plan

Before writing any code, state:
- What you found in git history and system files
- What feature you're working on and why
- What specific task you'll do this session
- Any blockers or questions

## Updating System Files

### Updating features.json

When starting work on a feature:
```json
{
  "id": "F001",
  "status": "in_progress",
  "notes": ["Started YYYY-MM-DD: Initial lexer structure"]
}
```

When completing a feature:
```json
{
  "id": "F001", 
  "status": "complete",
  "notes": ["Started YYYY-MM-DD: Initial lexer structure", "Completed YYYY-MM-DD: All tests passing"]
}
```

When blocked:
```json
{
  "id": "F001",
  "status": "blocked",
  "notes": ["BLOCKED: Need decision on how to handle heredoc edge case X"]
}
```

### Updating history.txt

Log significant actions as you work:
```
[2025-01-15 14:30] START: Beginning work on F001 (Lexer)
[2025-01-15 14:45] PROGRESS: Token enum defined, basic word tokenization working
[2025-01-15 15:30] DECISION: Using mode stack approach for quote handling
[2025-01-15 16:00] PROGRESS: Single and double quote modes implemented
[2025-01-15 17:00] BUG: Heredoc delimiter not detected when followed by comment
[2025-01-15 17:30] FIX: Added lookahead for heredoc detection
[2025-01-15 18:00] COMPLETE: F001 lexer complete, 47 tests passing
```

### Updating rules.txt

Add rules when you discover important constraints:
```
27. Heredoc content must be read AFTER the command line is fully parsed — not inline
28. SIGCHLD handler must be async-signal-safe — no allocations
```

## Session End Protocol

Before ending a session:

1. **Commit work** with descriptive message referencing feature ID
2. **Update features.json** with current status and notes
3. **Add history.txt entries** for all significant work done
4. **Summarize** what was accomplished and what's next

## Important Reminders

- ALWAYS read system files at session start — no exceptions
- ALWAYS update files as you work — not just at the end
- Feature IDs (F001, F002...) are permanent — never renumber
- History is append-only — never delete entries
- Rules accumulate — add discoveries, don't remove old rules
- When uncertain, add a DECISION entry explaining your reasoning
- When stuck, set status to "blocked" with clear description

Your effectiveness depends on maintaining this system. Future you (and other agents) rely on accurate tracking to understand context quickly.
